# SupportIQ Repository Instructions

## Project purpose

SupportIQ is a production-style enterprise AI customer-support platform and an
AI Engineering portfolio project. It is built incrementally so every backend,
database, infrastructure, and LLM decision can be explained and defended.

Do not introduce authentication, RAG, agents, frontend functionality, or other
roadmap components before their milestone is explicitly approved.

## Working approach

- Inspect relevant code, configuration, infrastructure, tests, and documentation
  before proposing a change.
- Explain the relevant concepts, request flow, design choices, and reasonable
  alternatives before implementation.
- Work on one small, reviewable milestone at a time.
- State which files will change and why before editing.
- Prefer simple, explicit, production-quality code over clever abstractions.
- Preserve working functionality unless its removal is explained and approved.
- Do not proceed to the next milestone without explicit user approval.

## Branch workflow

- `main` contains production-ready, released code.
- `develop` integrates completed work for the next release.
- Create each task branch from an up-to-date `develop`.
- Open task pull requests into `develop`.
- Merge `develop` into `main` only after the complete milestone is validated and
  approved.
- Create hotfix branches from `main`, then merge the fix into both `main` and
  `develop`.
- Do not commit directly to `main` or `develop`.
- Do not force-push shared branches.

Task branches use:

```text
<short-description>-SIQ-<issue-number>
```

Example:

```text
add-user-display-name-SIQ-12
```

Branch names must not contain spaces or square brackets.

## Commit convention

Use Conventional Commits with the SupportIQ issue identifier at the end:

```text
<type>(<scope>): <imperative description> [SIQ-<issue-number>]
```

Examples:

```text
feat(db): add database readiness check [SIQ-3]
test(db): verify session rollback behavior [SIQ-3]
docs(repo): document development workflow [SIQ-4]
```

Use focused commits with one clear purpose. Appropriate types include `feat`,
`fix`, `test`, `docs`, `refactor`, `ci`, `build`, and `chore`.

## Python and API standards

- Target Python 3.12 or newer.
- Use FastAPI, Pydantic Settings, SQLAlchemy 2.x style, Alembic, pytest, Ruff,
  and strict mypy.
- Use type hints throughout.
- Use synchronous database access unless measured concurrency requirements
  justify async complexity.
- Use dependency injection and explicit exception handling.
- Keep schemas, models, routes, services, and persistence concerns separate.
- Do not use `Base.metadata.create_all()` as a substitute for migrations.
- Do not silently commit database sessions inside shared infrastructure code.

## Testing and validation

Add or update tests with every functional change. Use unit tests for isolated
behavior and PostgreSQL integration tests for database behavior that SQLite
cannot faithfully prove.

Before a task is considered complete, run:

```text
ruff format --check .
ruff check .
mypy app tests
pytest -q
docker compose config
```

When Docker and PostgreSQL are required, also run the relevant migration,
integration-test, and image-build commands. Never suppress errors merely to
make validation pass.

## Database migrations

- Treat committed migrations as immutable shared history.
- Change models first, then generate a new Alembic revision.
- Review autogenerated upgrade and downgrade operations manually.
- Test migrations against a dedicated test database.
- Never perform destructive migration operations against shared or production
  data without explicit approval and a recovery plan.

## Security and repository hygiene

- Never commit secrets, `.env`, credentials, tokens, private keys, database
  state, Terraform state, virtual environments, caches, or generated package
  metadata.
- Load secrets through environment variables or an approved secret manager.
- Do not hardcode production credentials.
- Keep containers non-root and production images free of development tooling.
- Explain every new dependency and why the standard library or existing
  dependencies are insufficient.

## Milestone handoff

After implementation, report:

- what changed and why;
- how the request and dependency lifecycle works;
- commands used for validation and their results;
- expected output and common failure cases;
- one or two comprehension questions;
- a small exercise when it supports the learning objective.
